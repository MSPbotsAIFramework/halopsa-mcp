## Requirement understanding

One line: Add a tool to the HaloPSA connector that reads all actions/notes on a ticket (customer replies, technician notes, system events) with HaloPSA's native `/Actions` filters, matching the Rewst `halo_psa.list_actions` action used by the "Use OpenAI to Suggest Responses to Tickets" and several "Update Ticket" Rewst flows being migrated for the Ginko IT account.

Restatement: This ticket is item 7 of a Rewst-to-MSPbots migration gap register. Ginko IT's Rewst flows call HaloPSA's `GET /Actions?ticket_id={id}&excludesys=true` (plus ten other optional filter flags) to read a ticket's action history, which both an AI-reply-suggestion flow and nine webhook-driven "Update Ticket" flows depend on for context. The reporter checked all 26 tool descriptions on the already-connected HaloPSA MCP connector and found none that match; the closest, `halopsa_tickets_get`, is described only as "Get ticket details by ID". Success is: an MSPbots agent can call one tool, passing a ticket id and (optionally) HaloPSA's filter flags, and get back the actions HaloPSA would return for the equivalent Rewst call, including the fields the migrated flows read.

## Product design

### Goals / Non-goals

Goals:
- Add a read-only tool that returns a ticket's actions (notes, replies, system events) using HaloPSA's native `/Actions` filters, so an agent/SOP migrating from Rewst's `halo_psa.list_actions` can pass the same semantic filters (exclude system events, exclude private notes, agent-only, supplier-only, important-only, child-notes-only, include HTML note/email bodies, include attachment info, SLA-only, conversation-only) and get back the fields those flows need: who posted it and in what role, the note (plain and HTML), the outcome, old/new status, time taken, whether it is hidden from the end user, attachment count, and which action it replied to.
- Match the capability level of the vendor's own API for this one read path — not reinvent HaloPSA's filtering client-side. HaloPSA does the filtering; this tool is a pass-through with readable parameter names.
- Support paging through a ticket with many actions, consistent with every other list-shaped tool this server already has.

Non-goals:
- Not touching `halopsa_tickets_add_action` (the write path) or `halopsa_tickets_update`'s status-change behavior.
- Not changing `halopsa_tickets_get`'s existing `include_actions`/`actions_limit`/`actions_offset` behavior or its response shape — existing callers of that path see no difference (`AGENTS.md:19`: no removing parameters, no changing established behavior out from under existing callers).
- Not building a cross-ticket "list all actions in my tenant" tool — HaloPSA's own `/Actions` endpoint (and the ticket's own filter list) is ticket-scoped (`ticket_id` required); so is Rewst's `halo_psa.list_actions` call this migration is replacing.
- Not adding any UI. Per Current state, the platform surfaces a connector's tool list automatically; no app-side change is requested or needed.

### Acceptance criteria AC1..ACn

- AC1: Given a valid `ticket_id` for a ticket that has at least one action, When `halopsa_tickets_list_actions` is called with no optional filters, Then the tool returns a list of that ticket's actions (not another ticket's), each containing at minimum: `id`, `who`, `who_type`, `who_agentid`, `note`, `outcome`, `datetime`, `new_status`, `old_status`, `hiddenfromuser`, `timetaken` (with `time_taken_minutes` alongside, matching the existing `_action()` convention), `attachment_count`, `replied_to_action_id` — with fields HaloPSA did not send on that action simply absent, not null (matching this server's existing `pick()`/`slim()` convention everywhere else).
- AC2: Given a `ticket_id` for a ticket that has zero actions, When the tool is called, Then it returns an empty action list (not an error) — this is a different outcome than AC3's missing-ticket case, and the two must be distinguishable.
- AC3: Given a `ticket_id` that does not correspond to any ticket in HaloPSA, When the tool is called, Then it returns a `not_found` error naming the missing ticket, not an empty list (so a caller can tell "no actions" from "no such ticket").
- AC4: Given any of the eleven HaloPSA filter flags (exclude system events, exclude private notes, agent-only, supplier-only, important-only, child-notes-only, include HTML note body, include HTML email body, include attachment info, SLA-only, conversation-only), When the tool is called with one or more of them set, Then each one that was explicitly set is sent to HaloPSA as the corresponding native query parameter, and flags left unset are not sent at all (so HaloPSA's own defaults apply, same convention as every other optional filter on this server, e.g. `halopsa_tickets_list`'s `open_only`/`closed_only`).
- AC5: Given `include_html_note` or `include_html_email` is set true, When the tool is called, Then the HTML body field(s) HaloPSA returns for that action are included in the response rather than dropped by slimming (otherwise requesting them has no observable effect, defeating the parameter's purpose).
- AC6: Given a ticket has more actions than one page, When the tool is called without an offset, Then the first page is returned with a has-more indicator and a value the caller can pass back to continue — consistent with every other list tool in this connector (`_common.py` `window()`/`_result()`); calling again with that value returns the next page, and eventually a page with no more indicator.
- AC7: Given HaloPSA credentials are missing from the request, or the tenant/base URL is malformed, When the tool is called, Then it returns this server's standard `not_configured` error envelope — the same behavior every other tool already has, with no special-casing for this tool.
- AC8 (contract, non-functional): Given the connector's existing tools and `tests/fixtures/tools_baseline.json`, When this change ships, Then no existing tool loses a parameter, gains a new required parameter, or is renamed — only one new tool (`halopsa_tickets_list_actions`) and its own baseline entry are added, and `halopsa_tickets_get`'s `include_actions` path keeps returning exactly what it returns today.

### Open questions

- [not blocking, decided] The ticket's own response-field list (`who`, `who_type`, `who_agentid`, `note`, `note_html`, `outcome`, `datetime`, `new_status`, `old_status`, `hiddenfromuser`, `timetaken`, `attachment_count`, `replied_to_action_id`) is read as "the fields the consuming Rewst flows need," not as an exhaustive contract that excludes everything else. `id` is kept (it is not optional — pagination and `replied_to_action_id` both need it, and every existing action-returning path in this server already returns it). See Tech design Option analysis for the field-set decision.
- [not blocking] Whether HaloPSA's `/Actions` endpoint itself returns 404 for a nonexistent `ticket_id`, or silently returns `record_count: 0`, is not verified against a live tenant (no test account available, consistent with `references/mcp-track.md` §2.5/"completion standard" item 3 — this does not block design or dev). Assumption: treat it as returning zero rows either way, and add an explicit ticket-existence check (mirroring the `_missing_ticket` pattern already used for ticket writes, `tickets.py:156-158`) so AC2 and AC3 are reliably distinguishable regardless of what `/Actions` itself does. If a live-tenant self-test later shows `/Actions` already 404s on a bad `ticket_id`, the dev leg can drop the extra existence check as a one-fewer-HTTP-call simplification — flagged in Tech design Risks.
- [not blocking] The exact field names HaloPSA's live `/Actions` response uses for `who_type`, `who_agentid`, `old_status`, `attachment_count`, `replied_to_action_id` come from the ticket's own description (sourced from the reporter's Rewst integration), not from an independent live-tenant check. `pick()` (`_common.py:191-192`) silently drops any field not present in the record rather than erroring, so a misnamed field degrades to "that field is absent" rather than a crash; flagged in Test strategy as needing a real vendor account to fully confirm.

## Tech design

### Conclusion

Add one new read-only tool, `halopsa_tickets_list_actions(ticket_id, ...11 optional filters, limit, offset, full_response)`, to `src/halopsa_mcp/tools/tickets.py`, next to the existing action-related code. It calls `GET /Actions` with `ticket_id` plus whichever filters the caller set, reuses the existing over-fetch-and-slice pagination technique `halopsa_tickets_get` already uses for the same endpoint, and returns the standard list envelope (`window()`/`_result()`) every other list tool in this server already uses, with a richer action field set than `halopsa_tickets_get`'s `include_actions` path. No new file, no new dependency, no schema/DB change (this server is stateless and has none).

### Where the current implementation lives

- `src/halopsa_mcp/tools/tickets.py:217-259` — `halopsa_tickets_get`, whose `include_actions` path is today's only way to read actions; the pagination and field-slimming code this change reuses/extracts.
- `src/halopsa_mcp/tools/tickets.py:43-56` — `ACTION_FIELDS`, `DEFAULT_ACTIONS`, `MAX_ACTIONS` — the existing field set and page-size limits for actions.

- `src/halopsa_mcp/tools/tickets.py:174-215` — `halopsa_tickets_list`, the precedent for translating HaloPSA's own wire filter names into readable tool parameters (`halo_agent_id`→`agent_id`, `team_id`→`team`, `tickets.py:205-206`) and for a params dict built with `None`-dropping.
- `src/halopsa_mcp/tools/_common.py:52-86` — `Offset`, `_result()`, `window()`, `fetch_page()` — the shared list-result envelope; `window()` (`:70-73`) is the one this new tool's manual-slicing pattern maps onto directly (see Option analysis).

- `tests/fixtures/tools_baseline.json`, `tests/test_tools.py:34-42` — the tool-compatibility contract tests a new tool must satisfy by addition, not by exception.

### Option analysis

| Option | Do | Pros | Cost | Verdict |
|---|---|---|---|---|
| A: new tool in `tickets.py`, own richer field set | `halopsa_tickets_list_actions`, ticket-scoped, 11 filters passed straight through, new `LIST_ACTIONS_FIELDS` superset for slimming | Matches the ticket's ask exactly (dedicated tool, full filter set, full field set); does not touch `halopsa_tickets_get`'s established response shape for existing callers; keeps reads and writes for the same HaloPSA sub-resource (`/Actions`) in the same module, matching this repo's "one module per area" convention | One more tool in an already-large connector (27 → 28) | **Chosen** |
| B: extend `halopsa_tickets_get`'s `include_actions` path with the 11 new filters | Add the filters as more optional params on the existing tool | No new tool name | Conflates "get one ticket" with "query a ticket's actions" on a single signature that would then carry 15+ action-related parameters; any change to that path's response shape risks the exact kind of established-behavior break `AGENTS.md:19` forbids; a worse shape for an agent reasoning about "what tool do I call to read actions" | Rejected |
| C: a tenant/instance-wide `halopsa_actions_list` tool (not ticket-scoped) | A new top-level tool outside the `tickets` area | Mirrors some other areas' naming | HaloPSA's `/Actions` is inherently ticket-scoped (the ticket's own filter list requires `ticket_id`); Rewst's `halo_psa.list_actions` call this migrates is also per-ticket; inventing tenant-wide scope is unrequested, unbuildable (HaloPSA has no such endpoint) scope | Rejected |

Field-set decision (part of Option A): define `LIST_ACTIONS_FIELDS` as the existing `ACTION_FIELDS` plus the ticket's additional fields (`who_type`, `who_agentid`, `note_html`, `old_status`, `attachment_count`, `replied_to_action_id`), rather than extending `ACTION_FIELDS` itself. Extending `ACTION_FIELDS` in place would change `halopsa_tickets_get(include_actions=true)`'s response shape for existing callers of that tool — a bigger field set is backward-compatible in theory (callers reading named keys are unaffected), but `AGENTS.md:19`'s instruction not to "add required parameters" or otherwise disturb established tool behavior is read here as "don't let an unrelated ticket change a different tool's response shape," so the two field sets are kept independent. Cost: a small amount of duplication between `ACTION_FIELDS` and `LIST_ACTIONS_FIELDS` (both tuples share 10 of their fields) — judged acceptable over the risk of the two tools' call sites diverging more if they shared one tuple only to need different fields again later. If this call turns out wrong, unifying them is a same-day, single-file follow-up.

### Data & API contract

- New tool: `halopsa_tickets_list_actions`.
  - Request: `ticket_id: int` (required); `exclude_system`, `exclude_private`, `agent_only`, `supplier_only`, `important_only`, `is_child_notes`, `include_html_note`, `include_html_email`, `include_attachments`, `sla_only`, `conversation_only` (all `bool | None`, unset = not sent, HaloPSA's own default applies); `limit: int | None` (default 20, max 100 — same ceiling `MAX_ACTIONS` already enforces for `halopsa_tickets_get`); `offset: int | None`; `full_response: bool | None`.
  - Upstream call: `GET {Halo API}/api/Actions?ticket_id={id}` plus `excludesys`/`excludeprivate`/`agentonly`/`supplieronly`/`importantonly`/`ischildnotes`/`includehtmlnote`/`includehtmlemail`/`includeattachments`/`slaonly`/`conversationonly` for whichever of the 11 flags were explicitly set, and `count={offset+limit+1}` for the over-fetch — the same wire endpoint and method the ticket specifies.
  - Response (`full_response` false, default): `{"items": [...], "count": <int>, "limit": <int>, "offset": <int>, "has_more": <bool>, "next_offset": <int, if has_more>, "total_count": <int, if HaloPSA sent record_count>, "_resume": {...}}` — each item in `items` is `pick(action, LIST_ACTIONS_FIELDS)` plus `time_taken_minutes`: `id`, `who`, `who_type`, `who_agentid`, `note`, `note_html`, `outcome`, `datetime`, `new_status`, `old_status`, `hiddenfromuser`, `important`, `timetaken`, `time_taken_minutes`, `attachment_count`, `replied_to_action_id` — fields HaloPSA did not send on a given action are absent, not null (same convention as every other tool here).
    - Naming decision: HaloPSA's own `/Actions` response wraps the total as `record_count`; this server's universal list envelope (`_result()`, `_common.py:58-67`) names that field `total_count` on every other list tool. This tool keeps `total_count` for consistency with `halopsa_tickets_list`/`halopsa_clients_list`/etc. rather than introducing a one-off `record_count` key — additive relative to the ticket's wording (the information is present, under this server's existing name for it), not a removal. Flagged here, not an Open question, because it follows an existing, unambiguous server-wide convention.
  - Response (`full_response` true): HaloPSA's raw action objects, unslimmed — same convention as every other tool's `full_response` flag.
  - Errors: `not_configured` (missing/malformed credentials, AC7), `not_found` (ticket does not exist, naming it, AC3), `invalid_argument` (non-numeric `ticket_id` — `seg()`, `_common.py:165-171`, already raises `ToolInputError` for this, mapped to `invalid_argument` by `run()`), `upstream_error`/`rate_limited` for transient HaloPSA failures (existing `HaloClient` retry handling, no new code).
  - Backward compatibility: purely additive. No existing tool's request or response shape changes; `halopsa_tickets_get(include_actions=true)` keeps returning exactly `ACTION_FIELDS` as today.

### Key flow / sequence

```
Agent/SOP (migrated from Rewst halo_psa.list_actions)
  1. halopsa_tickets_list_actions(ticket_id=456, exclude_system=true)
  2. run() resolves credentials from request headers -> bound HaloClient (unchanged plumbing)
  3. _require(GET /Tickets/456)                      -- new: fails fast with not_found if 456 doesn't exist (AC3)
  4. _fetch_actions: GET /Actions?ticket_id=456&excludesys=true&count=21   (size=20, start=0)
  5. api.rows(payload, "actions"), api.record_count(payload)
  6. rows sliced [0:20], each mapped through pick(LIST_ACTIONS_FIELDS) + time_taken_minutes
  7. window(items, 20, 0) -> {"items": [...20...], "has_more": true, "next_offset": 20, "total_count": N, ...}
  8. run() serializes to a JSON string; any exception anywhere above is caught by run()'s existing
     handler and returned as the standard error envelope (no new error-handling code needed)
```

### Non-functional

- Idempotency/concurrency: read-only (`READ` annotation, same as `halopsa_tickets_list`/`_get`), stateless, no caching — consistent with "no module-level mutable state, no token cache" (`AGENTS.md:19`).
- Performance: two HaloPSA HTTP calls per invocation (the new ticket-existence check, plus `/Actions`) — one more than `halopsa_tickets_get`'s existing `include_actions` path, which only calls `/Actions` (it already has the ticket from its own `/Tickets/{id}` call, `tickets.py:242`). Page size capped at 100 (`MAX_ACTIONS`), same ceiling as today. HTML note/email bodies can be large; `full_response=false` (default) keeps responses bounded the same way `_action()` already does.
- Security/multitenancy: credentials come only from per-request headers via `credentials.current()` (`run()`), never cached or shared across requests — no new header, no new credential type, no code in `credentials.py` touched. This connector has no stored, cross-request state to isolate (`stateless_http=True`), so "multitenancy" here means "never cache credentials across requests," which this change does not touch.
- Observability: errors flow through the existing `_json.error()` envelope and `log.exception` in `run()` (`_common.py`) — no new logging needed.
- Backward compatibility: see Data & API contract — additive only; the dev leg must keep `tests/test_tools.py`'s baseline-compatibility tests green by adding (not modifying) a baseline entry.

### Rollout & rollback

- Single repo (`MSPbotsAIFramework/halopsa-mcp`), no cross-repo dependency, no platform-side change needed — `release order: any` is moot (nothing else has to ship in a particular order). Ships via the normal MCP flow: `dev/PRD-21575` → code review → merge to `main` → `mcppub publish` (already-registered vendor, per `mcp-track.md` §4.8) → INT.
- Once on INT, the new tool appears in the platform's per-connector tool inventory the next time a tenant refreshes that connector's tool list (wiki: `15-Capabilities.md` § Connector detail view, "Refresh Tools" control) — no platform-side deploy needed, no feature flag, no migration.
- Rollback: revert the merge commit on `main` and re-publish. The change is purely additive (one new tool, one new baseline entry), so rollback cannot break any existing agent/SOP that does not yet call the new tool.

### Effort & breakdown

Single-repo, mostly-single-module change (`tools/tickets.py` + `tools/meta.py` + `README.md` + baseline fixture + new tests + changelog entry). The new tool's shape follows 5+ existing tools in the same file almost exactly. Rough effort: 0.5–1 day for an engineer already familiar with this codebase. No sub-task split warranted.

### Risks & dependencies

- Risk: live field names and the not-found-vs-zero-rows behavior of `/Actions` are unverified against a real tenant (Open questions) — mitigated by `pick()` silently dropping absent fields, and by the explicit ticket-existence guard making AC2/AC3 reliable regardless of what `/Actions` itself does with a bad id.
