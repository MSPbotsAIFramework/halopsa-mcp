## Requirement understanding

One line: `mb-platform-agent`'s new contact-sync adapter for HaloPSA needs to enumerate every
contact (active and inactive) a tenant has, with every phone field, and (as a nice-to-have for a
future incremental sync, PRD-22108) search by phone number -- `halopsa_users_search` today can only
search by a non-empty name/email query and returns a narrower field set than a contact actually has.

## Current state (every claim carries path:line)

- `src/halopsa_mcp/tools/users.py:83-102` (pre-change `halopsa_users_search`): `query: str` is
  required (`:94`, `raise ToolInputError("query must not be empty.")` when blank) -- there is no way
  to ask for "every contact" through this tool. No phone-number search parameter exists.
- `src/halopsa_mcp/tools/users.py:16-26` (`CONTACT_FIELDS`) is the field set previously returned by
  this tool's own result shape via `fetch_page` -- it carries one `phonenumber` field, not the
  fuller set a contact can have.
- `src/halopsa_mcp/tools/users.py:28-52` (`CONTACT_DETAIL_FIELDS`) already exists (used by
  `halopsa_users_get`) and already carries every phone field: `phonenumber`, `phonenumber_preferred`,
  `mobilenumber`, `mobilenumber2`.
- `src/halopsa_mcp/tools/clients.py:37-52` (`halopsa_clients_list`) already supports an empty
  `search` (`:46`, `search: str | None = None`) -- companies can already be listed in full; this
  ticket does not change this tool.
- `src/halopsa_mcp/tools/_common.py:72-85` (`fetch_page`) already does offset-based pagination
  (`pageinate`, `page_size`/`limit`, `page_no`/`offset`, returns `next_offset`/`has_more`) -- no
  pagination change needed, only what gets passed into it and how the result is shaped afterward.

## Vendor API feasibility (HaloPSA's own public API docs, checked 2026-11-10 by the platform-side
design session, reproduced here since this repo's own change directly depends on it)

- `GET /Users` documented parameters include `search` (string), **`search_phonenumbers`** (bool --
  filter by a phone-number match on the search term), `client_id`, `site_id`,
  `includeactive`/`includeinactive`, and the same `pageinate`/`page_size`/`page_no` pagination
  (Halo Academy API docs, `haloacademy.halopsa.com/apidoc/resources/users`, retrieved via web
  search 2026-11-10) -- phone-based search is a real, documented vendor capability.
- A generic `datesearch` query parameter is documented for change detection
  (`usehalo.com/guides/article/?kbid=2358`) -- **not used by this change** (OQ2 in the platform-side
  design: incremental sync is split out to PRD-22108); noted here only so PRD-22108's own design
  does not have to re-discover it.
- Rate limit: Halo Academy's docs state 700 requests / 300 seconds (~140/min) per tenant; 429 is
  already retried (`src/halopsa_mcp/api.py:58-59`).

## Decisions made by DEV01

- **Widen the existing tool, don't add a new one.** `halopsa_users_search`'s `query` becomes
  optional (empty/omitted = list all, mirroring `halopsa_clients_list`'s own `search: str | None`
  pattern) and gains `search_phonenumbers: bool | None` as a straight passthrough to the vendor
  param above. Alternative considered: a separate `halopsa_users_list` tool — rejected as
  unnecessary duplication of one already-paged, already-filterable tool; `AGENTS.md`'s own rule
  ("do not rename tools, remove parameters or add required parameters") only restricts narrowing an
  existing contract, not widening it with optional parameters, which this change keeps to.
- **Response widened to `CONTACT_DETAIL_FIELDS` for every `halopsa_users_search` call, not only
  list-all calls.** Every existing caller of this tool already passes a non-empty `query` and reads
  only fields already inside `CONTACT_FIELDS` (a subset of `CONTACT_DETAIL_FIELDS`), confirmed by
  `grep -rn halopsa_users_search` across both this repo's own tests and the platform repo -- no
  caller breaks, and a single field-set keeps the tool's contract simple (one shape, not
  "detail fields only when query is empty"). Alternative considered: keep `CONTACT_FIELDS` for a
  name/email search and only widen for list-all -- rejected as a conditional contract that is harder
  to document and test for no real benefit.
- **`search_phonenumbers` requires a non-empty `query`** (raises `ToolInputError` otherwise) --
  it is a search-mode switch, not a filter; "match phone numbers against nothing" has no vendor
  meaning.
- **No new dependencies, no schema/credential change.**

## Data & API contract

```
Request (unchanged tool name "halopsa_users_search", new optional params):
  halopsa_users_search(
    query?: string,                 // now optional; omitted/blank = list all
    search_phonenumbers?: boolean,  // new: match query against phone fields instead of name/email
    client_id?: number,
    include_inactive?: boolean,
    limit?: number, offset?: number,
  )
Response (unchanged envelope shape -- items/count/limit/offset/has_more/next_offset; now the
detail field set):
  { "items": [ { "id", "name", "firstname", "surname", "title", "jobtitle", "department",
                 "emailaddress", "email2", "email3", "phonenumber", "phonenumber_preferred",
                 "mobilenumber", "mobilenumber2", "client_id", "client_name", "site_id",
                 "site_name", "inactive", "isimportantcontact", "linked_agent_id", "notes",
                 "customfields" ], ... }
Error (unchanged envelope): { "error": { "code", "message", "retryable" } }
```

## Risks

- `search_phonenumbers`'s real-world behavior is unverified against a live HaloPSA tenant (no test
  tenant was reachable from either this session or the platform-side design session). The platform

  ticket's Test notes before claiming the adapter works end to end; if HaloPSA's actual behavior
  differs from the documented param, this tool's implementation (not the platform-side contract)
  absorbs the difference in a follow-up.
