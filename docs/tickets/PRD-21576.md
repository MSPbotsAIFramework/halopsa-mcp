## Requirement understanding

One line: Add a halopsa_tickets_add_attachment tool to the HaloPSA MCP connector so Ginko IT's Rewst automations that upload a file to a ticket (via POST /Attachment) can be replicated on the MSPbots Agent Platform, per the Rewst-to-MSPbots migration gap register (mspbots-gap-register.xlsx, item 8).

Restatement: The ticket comes from an automated gap-register scan that diffs Rewst's HaloPSA actions against the MSPbots HaloPSA connector's tool list. It flags `halopsa_tickets_add_attachment` as a tool that needs to be added, describing the vendor endpoint (`POST {Halo API}/api/Attachment`), its input fields (`ticket_id`, `filename`, `data` required; `desc`, `note`, `type`, `action_id`, `user_id`/`agent_id`, `showforusers` optional), and citing four Ginko IT Rewst flows that call it (Windows 11 Compatibility Report — 1616 runs/365d, Billing Count Report — 37, M365 License Export — 8, Compromised User Response — 2). Success, as the ticket frames it, is: an agent can attach a file to a HaloPSA ticket the same way these four Rewst flows do.

## Current state (every claim carries path:line)

- `halopsa_tickets_add_attachment` already exists in this connector and is listed in the public tool table: `README.md:110`. It is implemented at `src/halopsa_mcp/tools/tickets.py:465-543` and documented in the "Behaviour notes" section at `README.md:160-166`.
- The tool calls `POST /Attachment` (`tickets.py:527`, matching the vendor endpoint the ticket cites) with a body built at `tickets.py:516-523`: `ticket_id`, `filename`, `data_base64` (the file content, base64-encoded), `content_type`, `isimage`, `showforusers`, and `action_id` when a note was also added.
- Parameter-by-parameter match against the ticket's own description of the Rewst call (`json_body: [{"ticket_id": "...", "filename": "...", "data": "... | base64", "showforusers": true}]`, quoted verbatim in the ticket):
  - `ticket_id` → `ticket_id: int` (`tickets.py:477`), validated to exist first (`tickets.py:504`, `_require(client, f"/Tickets/{tid}", ...)`) so a bad id returns `not_found` instead of a confusing upstream error.
  - `filename` → `filename: str` (`tickets.py:478`), sanitized by `_filename()` (`tickets.py:546-550`) to reject empty/`.`/`..`/path-like values.
  - `data` (base64) → `content: str` with `content_encoding: "base64"` (default) (`tickets.py:479-486`), decoded and size-checked by `_decode()` (`tickets.py:553-570`, 10 MB cap at `MAX_ATTACHMENT_MB`/`MAX_ATTACHMENT_BYTES`, `tickets.py:39`).
  - `showforusers` → `hidden_from_user: bool = True` (`tickets.py:493-495`), sent inverted as `showforusers` (`tickets.py:522`); the ticket's Ginko IT example passes `showforusers: true`, which this server reaches by passing `hidden_from_user=false`.
  - `type` (vendor's MIME type field) → `content_type: str | None` (`tickets.py:487-489`), defaulting to a guess from the file extension (`_guess_type`, referenced `tickets.py:501`) when omitted — the ticket's optional field, not used by any of the four cited Rewst flows.
  - `note` (vendor's note-on-the-attachment field) → `note: str | None` (`tickets.py:490-492`): when given, this server first creates a ticket action with that note (`tickets.py:508-515`) and links the attachment to it via `action_id` (`tickets.py:516-525`), rather than writing a bare `desc`/`note` value onto the `/Attachment` record directly. Same user-visible effect (the ticket gets a visible note plus the file) via a different vendor call shape. Not used by any of the four cited flows.
  - `desc` and an arbitrary existing `action_id` (vendor's "attach to an existing action") and `user_id`/`agent_id` (who performed the upload) have no direct equivalent today — see Non-goals and Open questions below. None of the four cited Rewst flows pass any of these three fields (the ticket's own Rewst call example only uses `ticket_id`, `filename`, `data`, `showforusers`).
- Error handling already covers the cases a migrated flow would hit: missing ticket → `not_found` without calling `/Attachment` (`tickets.py:504`, test at `tests/test_handlers.py:551-555`); oversized or invalid base64 → `invalid_argument` without calling `/Attachment` (`tickets.py:558-570`, tests at `tests/test_handlers.py:489-513`); a failed upload after a note was already created names the orphaned action in the error message (`tickets.py:528-531`, test at `tests/test_handlers.py:558-566`).
- Test coverage: 13 tests specific to this tool, `tests/test_handlers.py:447-566` (round-trip of base64 content, plain-text content, data-URL and explicit `content_type`, size limit at/over the cap, invalid base64, bad filename, note-links-to-action, `showforusers` visibility, missing ticket, and upload failure after a note was created). ## Product design

### Goals / Non-goals

- Goal: confirm that an MSPbots agent can reproduce the four cited Ginko IT Rewst flows' ticket-attachment step (upload a file to a ticket, optionally visible to the end user) using a HaloPSA MCP tool with the same required inputs the Rewst flows already send.
- Non-goal: full 1:1 parameter parity with every field HaloPSA's `/Attachment` endpoint accepts. `desc` (a plain description string separate from `note`), attaching to an **existing, caller-chosen** `action_id` (rather than one this tool creates for you), and `user_id`/`agent_id` (attributing the upload to a specific agent/user) are not used by any of the four flows this ticket cites. Adding parameters nobody has asked for yet is speculative work the gap register did not establish a need for (YAGNI) — see Open questions for what would change this.
- Non-goal: changing `halopsa_tickets_add_attachment`'s existing behavior for callers already using it for other tickets/PRDs. This ticket is additive-only in principle; in practice it requires no change at all (see Tech design §1).

### Acceptance criteria AC1..AC5

- AC1: Given a ticket that exists in HaloPSA, a file name, and its content as base64, When `halopsa_tickets_add_attachment` is called with `ticket_id`, `filename`, `content`, Then the server sends `POST /Attachment` with the decoded file as `data_base64` and the tool returns the attachment id — reproducing the Rewst "attach file to ticket" step with no missing required input.
- AC2: Given the Rewst flow wants the attachment visible to the end user (`showforusers: true`), When the tool is called with `hidden_from_user=false`, Then the request sent to HaloPSA has `showforusers: true`.
- AC3: Given a `ticket_id` that does not exist in HaloPSA, When the tool is called, Then it returns a `not_found` error and never calls `POST /Attachment`.
- AC4: Given the file content is not valid base64, or is larger than 10 MB after decoding, When the tool is called, Then it returns an `invalid_argument` error and never calls `POST /Attachment`.
- AC5: Given the exact field set the four cited Ginko IT Rewst flows use (`ticket_id`, `filename`, `data`, `showforusers` — no `desc`, `type`, `action_id`, `user_id`/`agent_id`), When each field is matched against `halopsa_tickets_add_attachment`'s parameters, Then every field used by those flows has a direct, working equivalent in the current tool (no new parameter is required to replicate them).

### Open questions

- [non-blocking] Should `halopsa_tickets_add_attachment` eventually accept `desc`, an existing `action_id` to attach to, and `user_id`/`agent_id`? Not blocking: no cited Rewst flow needs them today. If a future flow does, that is a new, concrete requirement for a follow-up ticket (see Tech design §11), not something to guess at now.

### Option analysis

No alternatives: the only question on the table is whether to do anything at all.

| Option | What it does | Why not |
|---|---|---|
| Add a second tool (e.g. `halopsa_tickets_attach_file`) that duplicates the same `POST /Attachment` call | New tool, same behavior | Violates the "don't duplicate" rule in SKILL.md's global code-quality requirement and `README.md`'s own design note ("Tool names and parameters match the previous HaloPSA connector... so existing agents keep working") — a second tool for the same capability only confuses which one to call |
| Rename or restructure the existing tool to look more "new" so the ticket shows visible code change | Cosmetic diff | Pure churn; no behavior changes, no test gets stronger, and it risks breaking the 13 existing tests and any agent already calling this tool by its current name |
| **Verify and close with no code change** (chosen) | Confirm parity, document it, hand to dev/review legs for a pass-through confirmation | Matches reality: the capability already exists and is already tested; this is what SKILL.md's "already covered" handling exists for |

### Data & API contract

Existing contract (unchanged), for reference:

Request (`halopsa_tickets_add_attachment` tool call):
```json
{
  "ticket_id": 5,
  "filename": "weekly-report.csv",
  "content": "<base64>",
  "content_encoding": "base64",
  "content_type": "text/csv",
  "note": null,
  "hidden_from_user": false
}
```

Sent to HaloPSA (`POST {instance}/api/Attachment`, `tickets.py:516-527`):
```json
[
  {
    "ticket_id": 5,
    "filename": "weekly-report.csv",
    "data_base64": "<base64>",
    "content_type": "text/csv",
    "isimage": false,
    "showforusers": true
  }
]
```

Tool response:
```json
{
  "ticket_id": 5,
  "attachment_id": 77,
  "filename": "weekly-report.csv",
  "content_type": "text/csv",
  "size_bytes": 1234,
  "hidden_from_user": false
}
```

Error envelope on a bad `ticket_id` or invalid content (unchanged, `tickets.py:504`, `:558-570`): `{"error": {"code": "not_found" | "invalid_argument", "message": "...", "retryable": false}}`.

Rewst → tool field mapping (the parity check behind AC5):

| Rewst/vendor field | Tool parameter | Notes |
|---|---|---|
| `ticket_id` | `ticket_id` | direct |
| `filename` | `filename` | direct |
| `data` (base64) | `content` (`content_encoding="base64"`, default) | direct |
| `showforusers` | `hidden_from_user` (inverted) | direct, opposite polarity |
| `type` | `content_type` | optional on both sides; not used by cited flows |
| `note` | `note` | optional on both sides; different vendor call shape (creates a linked action), same user-visible result; not used by cited flows |
| `desc` | — | no equivalent; not used by cited flows |
| `action_id` (attach to an existing action) | — | no equivalent; tool only creates its own action via `note`; not used by cited flows |
| `user_id` / `agent_id` | — | no equivalent; not used by cited flows |

No DB, no migration, no backward-compatibility concern — this repository has no database and no code changes are being made.

### Key flow / sequence

Unchanged, documented for completeness:

```
Rewst/Agent  ->  halopsa_tickets_add_attachment(ticket_id, filename, content, ...)
             ->  GET /Tickets/{ticket_id}        (existence check; 404 -> not_found, stop)
             ->  [if note given] POST /Actions   (creates a linked note action)
             ->  POST /Attachment                (uploads the file, linked to the action if one was created)
             ->  returns {ticket_id, attachment_id, filename, content_type, size_bytes, hidden_from_user}
```

### Non-functional

- Idempotency & concurrency: each call is one upload; HaloPSA's `/Attachment` endpoint is documented by the vendor as supporting update-by-id, but this tool does not expose an `id` parameter for that (not used by any cited flow, so not a gap for this ticket). No change.
- Performance: bounded by the existing 10 MB decode cap (`MAX_ATTACHMENT_BYTES`, `tickets.py:39`); unchanged.
- Security: credentials are read per-request from headers only, never logged or cached (SOP's three operating laws, unaffected by this ticket since nothing changes); the attachment content itself is never echoed back in the tool result (`tickets.py:539`, confirmed by `tests/test_handlers.py:459` asserting `"data_base64" not in json.dumps(out)`).
- Multi-tenant isolation: not applicable in the traditional sense — this is a stateless per-request MCP tool with no shared state between calls (SOP "run every call in isolation"); unaffected.
- Observability: unchanged; errors already return structured `{code, message, retryable}`.
