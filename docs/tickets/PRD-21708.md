# PRD-21708 · [Feature] Set contacts on HaloPSA tickets

## Requirement understanding

One line: Add a contact parameter (user_id) to halopsa_tickets_create so the contact found by halopsa_users_search can be set as the new ticket's contact, for migrating the Rewst workflow "[Ginko IT] M365: Alert on Login from Non-Native Country" to SOP 265.

Restatement: The reporter (Felix.Zhou@mspbots.ai) is migrating a Rewst automation to an MSPbots agent SOP. The Rewst version looks up a customer's "General User" contact and sets it as the ticket's contact when it files a HaloPSA ticket; the SOP cannot reproduce this step because `halopsa_tickets_create` has no contact-related parameter today, even though the agent can already find the contact with `halopsa_users_search`. Success is: the SOP passes the contact id it already has (example: 133) into `halopsa_tickets_create`, and the created ticket shows that contact as its requester — with no separate manual step. No other ticket-creation behavior should change.

## Current state (every claim carries path:line)

- `halopsa_tickets_create` (`src/halopsa_mcp/tools/tickets.py:261-302`) accepts `summary`, `client_id`, `tickettype_id`, `details`, `priority_id`, `halo_agent_id`, `site_id`, `category_1..4`, `full_response`, `team_id` — no contact/user parameter. This matches the reporter's list of current parameters verbatim (ticket "Problem / Pain Point" section).
- `halopsa_users_search` (`src/halopsa_mcp/tools/users.py:83-102`) returns contacts with the fields in `CONTACT_FIELDS` (`users.py:16-26`): `id`, `name`, `emailaddress`, `phonenumber`, `client_id`, `client_name`, `site_id`, `site_name`, `inactive`. The contact's id is returned as `id`, not `user_id` — the reporter's "`user_id`" refers to HaloPSA's own Ticket field name (next point), not a field returned by this search tool.
- HaloPSA's ticket already carries a contact reference under the key `user_id`: `TICKET_FIELDS` (`tickets.py:59-107`) includes `user_id`, `user_name`, `user_email` and `halopsa_tickets_get`/`halopsa_tickets_update` already read these back on an existing ticket (`tickets.py:217-253`, `:313-406`). So `user_id` is HaloPSA's native Ticket field for the contact, already round-tripped on read; `halopsa_tickets_create` is the only write path that does not expose it.
- `halopsa_users_get`/`halopsa_users_create`/`halopsa_users_update` (`users.py:104-207`) name the same entity's id parameter `contact_id`, not `user_id` — a naming choice made elsewhere in this server to avoid saying "user" for a HaloPSA contact. See Tech design §3 for why this ticket keeps `user_id` on `halopsa_tickets_create` instead of following that convention.
- Existing precedent for validating a foreign id before the write, so `/Tickets` does not fail with a confusing error: `client_id` is checked with `_require(client, f"/Client/{seg(client_id)}", ...)` before the POST (`tickets.py:279`); `team_id` is resolved to confirm it exists and to fetch the team's name, which HaloPSA also needs (`tickets.py:297-298`, `_team_fields` at `:625-636`). `docs/changes/2026-10-27-paging-records-errors.md` (repo doc, not re-verified against a live tenant) documents this as a deliberate pattern: "Writes to a missing ticket, contact or client return not_found ... `halopsa_users_update` and `halopsa_tickets_create` check the contact / client first, so no record is created by mistake." `halo_agent_id` and `site_id`, by contrast, are passed straight through with no existence check (`tickets.py:280-298`).

- `tests/test_tools.py:36-42` (`test_parameters_are_backward_compatible`) only asserts that `tests/fixtures/tools_baseline.json`'s parameters are a subset of the live schema and that no new parameter is required — adding an optional parameter does not require updating that fixture.

## Product design

### Goals / Non-goals

Goals:
- `halopsa_tickets_create` can set the new ticket's contact (HaloPSA's `user_id` field) from an id the caller already has, in the same call that creates the ticket — no separate step or workaround.
- The id accepted is exactly what `halopsa_users_search` / `halopsa_users_get` already return as `id`, so a caller (e.g. SOP 265) can chain "search contact -> create ticket with that contact" without any translation step.
- Passing an id that is not a real HaloPSA contact fails clearly, before any ticket is created, naming the id that was not found.

Non-goals:
- No new tool, and no change to any existing required parameter or to any other tool's behavior.
- No validation that the contact belongs to the same company (`client_id`) as the ticket being created. HaloPSA tickets already let `site_id` and `halo_agent_id` be set independently of `client_id` with no cross-check in this server; a contact/client cross-check would be new, un-requested scope. If HaloPSA itself rejects a mismatched combination, that surfaces as HaloPSA's own error text (same as any other HaloPSA-side rejection today).
- No change to `halopsa_tickets_update`. The ticket only asks for this on create; updating a ticket's contact after creation is a different, unrequested capability. (Non-blocking — see Open questions.)
- Not building or changing SOP 265 itself. This ticket only has to make the tool capable of what SOP 265 needs; wiring SOP 265 to call it is outside a connector repo change.

### Acceptance criteria AC1..ACn

- AC1: Given a valid `client_id`, `tickettype_id`, `summary`, and a contact id that is a real HaloPSA contact (as returned by `halopsa_users_search`/`halopsa_users_get`), When `halopsa_tickets_create` is called with that id as `user_id`, Then the tool succeeds and the created ticket, read back (`halopsa_tickets_get`), has `user_id` equal to the id that was passed.
- AC2: Given the same required fields and no `user_id` passed, When `halopsa_tickets_create` is called, Then the ticket is created exactly as it is today (no `user_id` sent to HaloPSA, no behavior change for any existing caller that does not pass this new parameter).
- AC3: Given a `user_id` that does not correspond to any HaloPSA contact, When `halopsa_tickets_create` is called with that id, Then the call fails with a `not_found` error that names the missing contact id, and no ticket is created in HaloPSA.
- AC4: Given `user_id` is passed together with other optional fields already supported by `halopsa_tickets_create` (e.g. `team_id`, `halo_agent_id`, `category_1`), When the tool is called, Then all of those fields are applied together — `user_id` does not override or get overridden by any of them.
- AC5 (contract): The change adds `user_id` as an optional parameter only. It does not rename `halopsa_tickets_create` or any existing parameter, does not make any existing parameter required, and does not use the reserved name `agent_id`. (`tests/test_tools.py` already enforces this for every tool.)

### Open questions

- [not blocking, decided] Parameter name is `user_id`, not `contact_id` (see Tech design §3 for the reasoning and the trade-off against the server's own `contact_id` convention elsewhere).
- [not blocking] Whether HaloPSA's `/Tickets` write needs anything besides a bare `user_id` (e.g. a companion name/email field, the way `team_id` needs `team`) is not verified against a live tenant — no HaloPSA test account is available in this environment. Assumption: a bare `user_id` is sufficient, because (a) every other id-only field on this same POST (`client_id`, `tickettype_id`, `priority_id`, `site_id`) is sent without a companion field, and (b) `user_id` is already read back as a bare field by `halopsa_tickets_get`. Per `references/mcp-track.md` §2.5/"completion standard" item 3, missing a vendor test account does not block design or dev; if the assumption is wrong, HaloPSA's own validation error surfaces through the existing error-mapping path (same as any other bad write), it does not fail silently or write partial data.
- [not blocking] Extending `halopsa_tickets_update` with the same `user_id` parameter (to change a ticket's contact after creation) is a natural follow-up but is outside this ticket's asked-for scope (create-time only). Flagged as a suggested follow-up ticket, not built here.

## Tech design

### Conclusion

Add one new optional parameter, `user_id: int | None = None`, to the existing `halopsa_tickets_create` tool in `src/halopsa_mcp/tools/tickets.py`. Validate it exists (same `_require` helper already used for `client_id`) before posting, then pass it straight through as HaloPSA's own `user_id` ticket field. No new tool, no new file, no new dependency, no schema/DB change (this server is stateless and has none) — a same-shaped, same-style addition to the one function that needs it.

### Where the current implementation lives

- `src/halopsa_mcp/tools/tickets.py:261-302` — `halopsa_tickets_create`, the tool being changed.
- `src/halopsa_mcp/tools/tickets.py:607-614` — `_require(client, path, message)`, the existing missing-record-guard helper, already used at `:279` for `client_id`; reused as-is for `user_id`, no changes to the helper itself.
- `src/halopsa_mcp/tools/tickets.py:124` — `AgentId = Annotated[int | None, Field(description=HALO_AGENT_ID_DESC)]`, the closest existing precedent for a described, optional, id-only `Annotated` type on this tool; the new `user_id` type follows the same shape.
- `src/halopsa_mcp/tools/_common.py:28-30` — `HALO_AGENT_ID_DESC`, the style this change's own description constant follows (one sentence: what the id is, where it comes from, what it is not).
- `src/halopsa_mcp/tools/users.py:104-117` — `halopsa_users_get(contact_id: int, ...)`, the tool that already returns/accepts this same HaloPSA entity under the name `contact_id` (relevant to the naming decision in §3, not touched by this change).
- `tests/test_handlers.py:153-177` — `test_tickets_create_maps_agent_and_team`, the existing test exercising `halopsa_tickets_create`'s optional-field mapping; the pattern the new tests follow.
- `tests/test_records.py:215-219` — `test_tickets_create_for_a_missing_client_is_not_found_and_writes_nothing`, the existing test for the `client_id` not-found path; the pattern the new `user_id` not-found test mirrors.

### Option analysis

No real alternative design — this is a single, already-conventional addition to an existing tool, not a new capability that needs a shape decision. The one actual decision is the parameter's name:

| Option | Do | Pros | Cost | Verdict |
|---|---|---|---|---|
| A: `user_id` | Keep HaloPSA's native Ticket field name, exposed as-is | Matches what `halopsa_tickets_get`/`_update` already read back (`tickets.py:77-79`); matches the reporter's confirmed acceptance check verbatim ("accepts the contact through user_id"); zero translation between the tool's input and HaloPSA's own wire field | Inconsistent with `halopsa_users_get`/`_create`/`_update`'s `contact_id` naming for the same underlying entity, on a different tool | **Chosen** |
| B: `contact_id` | Rename to match the contacts-domain tools' convention | Consistent naming for "this HaloPSA entity" across the whole tool surface | Diverges from HaloPSA's own `user_id` wire field (would need a rename at the API boundary, the opposite of every other id field on this tool, which are all named after HaloPSA's own field); diverges from the reporter's confirmed, as-written acceptance check | Rejected |

Decision: Option A. The description on the new parameter spells out that it is the same id `halopsa_users_search`/`halopsa_users_get` call `id` (not `contact_id`) and that it sets what HaloPSA calls the ticket's `user_id`, so the naming mismatch with the contacts tools is documented at the point an agent would be confused by it, rather than hidden. This is a small, reversible choice (the parameter does not exist yet, so there is no compatibility cost to picking one name now); flagged in Product design Open questions, not blocking.

### Data & API contract

- Tool: `halopsa_tickets_create` (unchanged name, unchanged annotations `CREATE` = `readOnlyHint=False, destructiveHint=False, idempotentHint=False, openWorldHint=True`, `tickets.py:21`/`:258`).
- New parameter: `user_id: int | None = None` (optional, nullable; omission or `null` preserves today's behavior exactly).
- HaloPSA wire call: `POST /Tickets` (unchanged endpoint). Request body gains one key when `user_id` is supplied: `{"user_id": <int>, ...rest unchanged...}`. HaloPSA's public contact-id validity check happens through the same `GET /Users/{id}` pre-check already used for `client_id` against `GET /Client/{id}` (`tickets.py:279`); on a miss, the tool raises `api.ApiError("not_found", "No contact <id> in HaloPSA.", False, 404)` (same shape `_missing_ticket()` already uses for tickets, `tickets.py:150-152`), which the server's existing error envelope (`_json.py`, unmodified) turns into the standard `{"error": {"code": "not_found", ...}}` response — no new error code.
- Response: `halopsa_tickets_create`'s return value is unchanged in shape; `user_id`/`user_name`/`user_email` are already in `TICKET_FIELDS` (`:59-107`) and already appear whenever HaloPSA's created-ticket response carries them, so a ticket created with a contact now shows that contact on the same response, no slimming/field-list change needed.
- Backward compatibility: every existing caller that does not pass `user_id` sees byte-for-byte the same request body and response shape as before (verified by the Change list's `test_tickets_create_without_contact_omits_user_id`).

### Key flow / sequence

```
SOP 265 (or any caller)
  1. halopsa_users_search(query="<customer contact name/email>")       -> contact.id (e.g. 133)
  2. halopsa_tickets_create(summary=..., client_id=..., tickettype_id=..., user_id=133)
       -> _require(GET /Users/133)            # new: fails fast with not_found if 133 is not a real contact
       -> _require(GET /Client/<client_id>)   # unchanged, existing check
       -> POST /Tickets [{..., "user_id": 133}]
       -> ticket returned, user_id: 133 (and user_name/user_email, if HaloPSA fills them)
  3. (optional) halopsa_tickets_get(ticket_id) -> user_id still 133, confirming AC1
```

Both `_require` calls are read-only GETs before the single `POST /Tickets` write, so a missing contact or a missing client is reported without creating a partial/incorrect ticket, consistent with the existing `client_id` behavior.

### Non-functional

- Idempotency / concurrency: unchanged. `halopsa_tickets_create` was already `idempotentHint=False` (each call creates a new ticket); adding an optional field does not change that. No shared/module-level state is touched (this server is stateless per request, `AGENTS.md:19`).
- Performance: one additional `GET /Users/{id}` call, only when `user_id` is supplied — same cost class as the existing `GET /Client/{id}` call already made on every create. No new pagination, no new loop.
- Security: credentials are unaffected — this change does not touch `credentials.py` or the per-request header handling. The new parameter is a plain integer id scoped to the tenant identified by the request's own HaloPSA credentials (the same tenant `client_id`/`site_id`/`halo_agent_id` are already scoped to); there is no cross-tenant surface here beyond what `client_id` already has, because HaloPSA's own API key/tenant resolution — not this parameter — determines which HaloPSA instance's `/Users` and `/Tickets` are reached.
- Multi-tenant isolation: not applicable in the Agent Platform's schema-per-tenant sense — this is a vendor MCP server; isolation here is "credentials only from the request's own headers, never cached" (`AGENTS.md:19`, SOP's three-rule "运行模型"), which this change does not touch at all (no credential code is modified).
- Observability: no new logging is added or needed; failures surface through the existing `not_found` error envelope, which is already visible to the calling agent/SOP as a tool-call error.

### Rollout & rollback

- No feature flag: this is an additive, optional parameter behind the agent's own choice to pass it; there is no user-facing surface to gate.
- Release order: single repo (`MSPbotsAIFramework/halopsa-mcp`), no cross-repo dependency, no platform-side change — `release order: any` is moot here (nothing else needs to ship in a particular order).
- Rollback: revert the one commit on `main`; `user_id` simply stops being accepted (older callers that never pass it are unaffected either way, since the new tests also assert the no-`user_id` behavior is unchanged while `user_id` support exists).

### Risks & dependencies

- Risk: HaloPSA's actual `/Tickets` contract might need more than a bare `user_id` to make the contact "stick" (the way `team_id` needed a companion `team` name, per `_team_fields`, `tickets.py:625-636`). Mitigation: documented as a non-blocking, explicit assumption (Open questions); if wrong, it fails loudly as a HaloPSA-side error on the next real call, not silently.
- Risk: none identified around multi-tenant or security, since this change reuses the same credential/tenant path already used by every other parameter on this tool.
- Dependency: none on another ticket or repo. Single-repo, single-tool change.
- Not a risk, but worth recording: the reporter's own intake flagged `openviking wiki retrieval is unavailable in this session` and that duplicate-search coverage against `901716477471`/`901715062360` was not exhaustive (`last_page=false`).
