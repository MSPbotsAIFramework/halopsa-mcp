## Requirement understanding

One line: Add a new tool halopsa_sla_get to the existing HaloPSA connector/MCP that reads an SLA's details -- including that SLA's priority list -- by SLA id, used to resolve a priority name to its id.

This ticket is item 9 of the Rewst → MSPbots migration gap register (`mspbots-gap-register.xlsx`), raised against the Ginko IT Rewst account. It is a "tool" gap: the HaloPSA connector/MCP is already connected (26 tools), but none of them cover this capability — the requester checked all 26 tool descriptions one by one and found no match. The Rewst flow this replaces calls HaloPSA directly: `GET {Halo API}/api/SLA/{id}?includedetails=true`, taking `sla_id` (required integer, Ginko's own default is `1`, variable `halo_sla_id`) and `includedetails=true`, and reading back the SLA's `id`, `name` and `priorities[]` (`id`, `name`, `responsetime`, `fixtime`, `colour`). It is used by Ginko IT's "PSA: Get Ticket Priorities" sub-flow (called by "AI Sentiment" and "AI Ticket Categorization", ~365 runs/year, evidence level A per the gap register) to turn a priority name into the id HaloPSA expects elsewhere. Success is: an MSPbots agent can call a new MCP tool with an SLA id and get back the same information this Rewst flow gets today, so the flow can be migrated off Rewst.

  async def halopsa_invoices_get(invoice_id: int) -> str:

      return await run(settings, handler)

## Product design

### Goals / Non-goals

Goals:
- Add one new read tool, `halopsa_sla_get`, that given an SLA id returns that SLA's `id`, `name`, and its `priorities` array (`id`, `name`, `responsetime`, `fixtime`, `colour`), so an agent can resolve a priority name to the id HaloPSA expects elsewhere (e.g. before calling `halopsa_tickets_create`/`_update`).
- Match the Rewst flow's input/output exactly: one required integer `sla_id`, `includedetails` behaviour always on (the only use case needs it; no reason to expose it as a toggle).

Non-goals:
- Not adding a "list all SLAs" tool (`GET /api/SLA` without an id). The ticket mentions this sibling endpoint exists, but neither the ticket nor its one cited caller (Ginko IT's "PSA: Get Ticket Priorities" sub-flow) needs it. See Open question Q2.
- Not changing `halopsa_lookups_get` or any other existing tool's behaviour or shape.

### Acceptance criteria AC1..ACn

- **AC1**: Given a valid `sla_id` that exists in the tenant, when `halopsa_sla_get` is called with it, then the result includes `id`, `name`, and a `priorities` array where each item carries `id`, `name`, `responsetime`, `fixtime`, `colour` (when HaloPSA sends a non-empty value for each).
- **AC2**: Given an `sla_id` that does not exist in the tenant, when `halopsa_sla_get` is called, then the tool returns a structured `not_found` error (the shared error envelope), not a raw exception and not an empty object disguised as success.
- **AC3**: Given a missing or non-numeric `sla_id`, when `halopsa_sla_get` is called, then the tool returns `invalid_argument` without making any HTTP call to HaloPSA.
- **AC4**: Given per-request credential headers for one tenant, when `halopsa_sla_get` is called, then the result reflects only that tenant's HaloPSA instance — no caching or state is shared across requests/tenants (same isolation guarantee every existing tool in this server provides; nothing new is introduced by this tool).
- **AC5**: Given the new tool is added, when `tools/list` is called, then `halopsa_sla_get` appears with `readOnlyHint=true`, `destructiveHint=false` (consistent with every other `*_get` tool), and every existing tool's name, required parameters and parameter types are unchanged (backward compatible).
- **AC6**: Given an SLA with an empty `priorities` list, or a priority row missing some of `responsetime`/`fixtime`/`colour`, when `halopsa_sla_get` is called, then the tool returns `"priorities": []` (not an error) and omits the fields HaloPSA did not send for a given priority (consistent with `slim()`'s behaviour used by every other `_get` tool).

### Open questions

- **Q1 (not blocking; assumption applied)**: Should `sla_id` default to `1` when omitted, matching Ginko IT's own Rewst default? **Assumption: no** — every other `*_get` tool in this repo (`halopsa_invoices_get`, `halopsa_assets_get`, etc.) requires its id explicitly; defaulting an id server-side risks silently returning the wrong SLA's data to a caller who forgot the parameter. If product wants a default, say so in a comment and move this ticket back to `5b - ready for groom`.
- **Q2 (not blocking)**: Should a `halopsa_sla_list` tool (`GET /api/SLA`, no id) be added at the same time? **Decision: not now** — nothing in this ticket or its cited caller enumerates SLAs; adding it would be speculative. File a follow-up ticket if a future flow needs it.

## Tech design

### Conclusion

Add one new read tool, `halopsa_sla_get(sla_id: int) -> str`, to `src/halopsa_mcp/tools/lookups.py` (same module as the existing reference-data tool `halopsa_lookups_get`), calling `GET /SLA/{sla_id}?includedetails=true`, following the exact `halopsa_invoices_get` pattern already in this repo. Register it in the `lookups` domain and in the contract-test baseline fixture.

### Option analysis

- **Option A (chosen)**: Add `halopsa_sla_get` as a new function inside `tools/lookups.py`, in the existing `lookups` domain. Reuses `slim`, `seg`, `run`, `READ`, `api.first` exactly like `halopsa_invoices_get` — minimal new code, and the `lookups` domain's stated purpose ("read the tenant's reference data ... so ids are resolved live") already matches this tool almost verbatim.
- **Option B (rejected) — new module + new domain**: `tools/sla.py` + a new `sla` entry in `DOMAINS`. Rejected: a one-tool domain grows `halopsa_navigate`'s domain enum and the `DOMAINS` dict for no benefit; there is no second SLA tool planned (see Q2).
- **Option C (rejected) — extend `halopsa_lookups_get` with an `sla_id` filter instead of a new tool**: The endpoint that tool calls, `GET /Priority` (`lookups.py:134`), returns the flat priorities list without `responsetime`/`fixtime`/`colour` (`lookups.py:19-21`). Satisfying AC1 this way would still need a second upstream call to `/SLA/{id}` (making the "filter" option pure indirection, not a saving), or would require changing `FIELDS["priorities"]`'s shape for every existing caller of `halopsa_lookups_get` — a behaviour change to a tool `AGENTS.md` says must stay stable ("Do not rename tools, remove parameters..."). A dedicated tool matching Halo's own `/SLA/{id}` resource is more direct and matches how every single-entity lookup in this repo already works.

### Reuse & cleanup

- **Reuse**: `slim()`, `seg()`, `run()`, `READ`, `api.first()` — no new HTTP client code, no new dependency; the new tool is the same shape as `halopsa_invoices_get`.
- **New deps**: none.
- **API/param shape**: one new tool, one required parameter (`sla_id: int`); no existing tool's signature, required parameters, or response shape changes — fully additive (AC5).
- **In-scope cleanup**: none needed — `lookups.py` and `meta.py` are small and current; nothing dead is touched by this change.
- **Out-of-scope follow-ups** (list, don't fix here): a possible future `halopsa_sla_list` tool if a ticket ever needs to enumerate SLAs (Q2) — not filed as a separate ticket since there is no current need, just recorded here.

### Data & API contract

- New tool: `halopsa_sla_get(sla_id: int) -> str` — JSON string, same envelope convention as every other tool in this server.
- Upstream call: `GET {Halo API root}/SLA/{sla_id}?includedetails=true` (HaloPSA's documented SLA resource; the ticket's sibling `GET /api/SLA` list endpoint is out of scope, see Non-goals).
- Success shape, after `slim(api.first(...))` (empty/related fields trimmed, same as every other `_get` tool):
  ```json
  {"id": 1, "name": "Gold SLA", "priorities": [
    {"id": 1, "name": "Critical", "responsetime": 15, "fixtime": 240, "colour": "#ff0000"}
  ]}
  ```
- Errors, via the shared envelope in `run()`: `not_found` (unknown `sla_id`, Halo 404), `invalid_argument` (non-numeric `sla_id`, raised by `seg()` before any HTTP call), `unauthorized` (missing/invalid credential headers), `upstream_error` (Halo 5xx or a non-JSON response).
- Backward compatibility: purely additive — no existing tool's request or response shape changes.

### Key flow / sequence

1. **Today**: Ginko IT's Rewst flow calls Halo directly — `GET /api/SLA/{halo_sla_id}|d(1,true)}?includedetails=true` via the `halo_psa.generic_request` action.
2. **After this change**: an MSPbots agent calls `halopsa_sla_get(sla_id=<id>)` → the MCP resolves the tenant's credentials from the request headers (`credentials.current()`, same as every tool, no caching) → calls the same HaloPSA endpoint → `slim(api.first(...))` → a JSON string is returned to the agent → the agent reads `priorities[].name` / `priorities[].id` to resolve a priority name to its id, mirroring what the Rewst sub-flow does today.

### Non-functional

- **Multi-tenant isolation**: unchanged. Credentials come only from per-request headers (`credentials.current()`); nothing is cached or shared across requests or tenants — same guarantee every tool in this stateless server already provides (the SOP's header-only-credentials / no-disk-or-log / per-request-isolation rules). No new state is introduced.
- **Idempotency/concurrency**: a read-only `GET`, naturally idempotent; marked `READ` (matches `test_annotations`'s rule that `_get`-suffixed tools are read-only).
- **Performance**: one upstream call per invocation, same cost as `halopsa_invoices_get`/`halopsa_assets_get`. `includedetails=true` on a single SLA returns a handful of priority rows — no pagination, no risk of hitting `_json`'s 20k-char cap that list endpoints guard against.
- **Security**: no new credential handling. `seg()` rejects anything that is not a plain positive integer before it reaches the URL path, so `sla_id` cannot be used for path injection — the same guard already used by every other `_get`/`_update` tool that takes an id.
- **Logging/observability**: unchanged — errors flow through the existing `_json.error()` envelope and the `log.exception` path in `_common.run()`; no new logging needed.

### Rollout & rollback

- Pure addition (new tool function, one new `DOMAINS` entry, one new baseline-fixture row); no migration, no feature flag, no other repo depends on this change (`Track: vendor-mcp`, single repo — no cross-repo release ordering applies).
- Rollback: revert the commit. No data changes to undo. If the deployed server is rolled back, callers of `halopsa_sla_get` simply see it missing from `tools/list` again, same as before this ticket.

### Test strategy

- **Unit** (`tests/test_handlers.py`): new tests against a mocked `/SLA/{id}` via `respx_mock` — success with full fields (AC1), success with a priority missing `colour`/`fixtime` and an SLA with an empty `priorities` list (AC6), 404 → `not_found` (AC2), non-numeric `sla_id` → `invalid_argument` with no HTTP call recorded (AC3).
- **Contract** (`tests/test_tools.py`, existing, parametrized over every registered tool): automatically covers the new tool once `tools_baseline.json` is updated — baseline membership, backward-compatible schema, annotations, navigate-domain coverage, no `agent_id` parameter, description length (AC5).
- **Manual/integration**: verifying the live response shape end-to-end needs a real HaloPSA tenant with at least one configured SLA; no vendor test account is available in this environment. Does not block (`references/mcp-track.md`: "a missing vendor test account is not a blocker"); the `.ac.json` entry for this is marked `needs a real vendor account`.
- **Regression**: full suite (`uv run pytest -q`) run on the branch after merging the latest default branch in, per the dev leg's gate; the `tools/list` smoke test will show 27 tools (26 existing + 1) instead of 26.

### Effort & breakdown

Small, single-commit scope: one tool function, one `DOMAINS` edit, one baseline-fixture edit, a handful of unit tests, one change-log entry, one README edit. No sub-task split needed.

### Risks & dependencies

- **Risk**: HaloPSA's `/SLA/{id}` response shape for `priorities[]` could vary slightly between hosted/on-prem instances (Halo's API docs are schema-light). Mitigated by reusing `slim()`'s tolerant "keep what's sent, drop what's empty" behaviour already used for every other entity in this server, rather than hardcoding a strict field list.
- **Risk**: no live tenant available to verify against in this environment (see Test strategy) — flagged, not blocking.
- **Dependency**: none on other tickets or repositories. `Track: vendor-mcp`; release order: n/a (single repo).
